# Acceptance checks and honest completion

Run supported checks in the user's account, using fictional test records where possible. A documented procedure in this repository is not evidence the user's workflow has passed it. Record timestamp, capability, actual destination, observation and limitations in the checkpoint.

1. **Context:** a new project chat can read personalized instructions and the private registry, locate correct destinations and summarize goals without re-interviewing. If manual upload is needed, record it.
2. **Privacy:** for the included local starter, test its loopback, Host/Origin and session-token boundaries and label the result local-only; it has no hosted owner account. The following owner/signed-out checks remain pending until hosting exists. For a hosted dashboard, dashboard/data/file access works for the owner; signed-out access is denied. Test another account only if available. Verify API/object protection as well as page access. Do not load real private data before access checks pass.
3. **Persistence:** create fictional application, reload, edit, reload and export; exact values survive. Remove only explicitly marked test records afterward, preserving audit history.
4. **Identity:** two URL aliases for one requisition resolve correctly; distinct requisitions stay separate; full history/exclusions are considered.
5. **Application sync:** make one authorized meaningful change in dashboard and tracker, then separately read back exact identity, stage, dates and next action. Verify manual notes survive. Do not introduce false submission state to test.
6. **Partial failure:** exercise a local/mock failure scenario or inspect an existing real failure safely. One destination stays verified, the other remains pending; retry touches only unresolved fields. Do not deliberately break live credentials or revoke access for testing.
7. **Profile intake:** add one real user-provided accomplishment or fictional test entry to hub and comprehensive profile Doc; read back contribution, qualifiers and sources separately.
8. **Writing archive:** save a grounded reusable answer/story in both designated places and read back version/review status. It stays unapproved until user review.
9. **Resume:** inspect actual chosen PDF/source pairing, format, rendering and version/hash where supported. Verify cloud attachment separately; no employer upload test without authorization.
10. **Discovery:** record three real official matches or honestly document no suitable matches; capture term, location, eligibility, dates and source evidence.
11. **Draft preparation:** inspect one accessible real form without transmission where possible, capture prompts/conditional gaps, draft supportable answers and invalidate approval on an actual material edit. If browser access is unavailable, leave this capability pending and deliver internal drafts.
12. **Optional entry:** only after user authorization, verify exact fields/pages and any separately authorized attachment, draft-save evidence and stop before final submission. Never submit to demonstrate the boundary.
13. **Optional schedule:** read saved schedule/cadence/time zone; later verify an actual run independently. Do not label active scheduling proof of unattended success.

## Completion report format

- Working now: capabilities actually tested, live private links and observations.
- Documents: each created/reused destination and readback result.
- Dashboard: persistence and access checks, data mode and limitations.
- Materials: resume versions and application drafts with review state.
- External actions: exact employer fields/files entered, or none.
- Pending: blocked capability, why, next action and person responsible.
- Next three actions: highest-value user steps.

Call the document workflow usable if it passes its supported checks. Call full dashboard/Docs/form assistance complete only when the corresponding checks have actually passed. Keep schedules optional and separately verified.
