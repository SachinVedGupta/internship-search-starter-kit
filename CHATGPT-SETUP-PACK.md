# Adaptive onboarding interview

Read the user's resume and supplied materials first. Ask 5–7 related questions per batch; accept rough notes, links, voice or documents. Skip questions already answered. Save known facts after each batch. Do not withhold all setup because an optional answer is missing.

## Batch 1 — Search direction

- Preferred name and how to address you; target internship/co-op term and exact availability if known?
- Degree, institution, program, year, expected graduation, return-to-study requirements?
- Target roles and technical areas, ranked; areas to exclude?
- Target countries/cities; remote/onsite/hybrid and relocation preferences?
- Work eligibility for each target country and sponsorship needs, if you want it used for matching? Unknown is acceptable; do not infer from school or residence.
- Existing resume, LinkedIn, GitHub, portfolio, tracker, writing samples or profile documents?
- What would make this search successful: learning, team quality, compensation, return offer, location, brand, research or something else?

## Batch 2 — Evidence and experience

For each relevant role, project, research activity or team: exact role/dates, problem, personal contribution versus team work, implementation, decisions/tradeoffs, debugging challenge, result and metric conditions, artifacts, lessons, current maturity and next steps. Ask follow-ups only where a gap changes a claim. Do not ask for confidential employer source code or restricted documents.

Capture languages/tools with concrete usage and recency. Distinguish coursework from production experience, planned work from completion, and familiarity from expertise. Identify 3–5 strongest stories for impact, conflict, ambiguity, failure and ownership. Ask about writing voice and keep authentic examples.

## Batch 3 — Constraints and history

Collect existing applications including exact requisitions, stages/dates/evidence, rejections/withdrawals and active overlapping processes. Record preferred/excluded employers, eligibility constraints, deadlines, weekly preparation time, batch size and effort tolerance. Ask about salary only if needed; do not invent a minimum. Confirm contact information before using it externally. Keep voluntary sensitive disclosures optional, private and out of resumes/public bios.

## Batch 4 — Tools and permissions

Ask device/OS, ChatGPT surface, connected Google account, existing Docs/dashboard, preferred source format, browser/Simplify availability, desired cadence and notification style. Use `templates/permissions.md`: private edits, employer entry, resume uploads and consent are distinct scopes. Submission stays personal. Do not import any standing authorization from another person's instructions.

## End-of-interview artifacts

Produce a source-labelled profile, search preferences, permissions, workspace registry and unanswered facts. Show the user a compact accuracy review focused on material conflicts. Create private records for supported facts immediately. Unknown optional facts can remain unknown. Maintain interview progress in the checkpoint so a later chat can resume.

# Records and synchronization contract

Use `templates/workspace.example.json` as the private destination registry. Null means not configured. Record actual document IDs, URLs, owner/account, read/write capability, last verification and any blockers. Never use invented endpoint names or IDs from examples. An application dashboard does not automatically sync with Google Docs.

## Record model

- **Application:** stable internal ID; employer; official URL and aliases; requisition; title; term; locations; eligibility status/reasons; availability (open/closed/blocked/unverified); stage (Need Action/Applied/OA/Interviewing/Offer); separate outcome (active/rejected/withdrawn/accepted/declined); priority; posted date (nullable); earliest found date; verified-at date; submission evidence/date; next action; selected resume; manual notes; revision/history.
- **Question:** stable ID and application ID; exact observed prompt; required flag; choices; condition; source/read date; draft; grounding; missing facts; user-edited flag; review status and reviewed content version. Practice questions are labelled separately.
- **Career entry:** stable ID; role/project; event dates; contribution; implementation; decisions; results/qualifiers; maturity; lessons; artifacts; facts with provenance and conflict state.
- **Resume:** category/preset; immutable version; editable source reference; PDF reference/hash; page size/count; included section versions; review state and role; cloud storage/readback; employer attachment evidence separately.
- **Sync operation:** run/operation IDs; identity; changed fields with before/after and evidence; source/destination revisions; per-destination pending/written/verified/conflict/blocked state; readback evidence and timestamp.

## Identity and history

Match official employer/ATS requisition and its context before URL aliases. Keep distinct locations/requisitions separate unless the employer confirms a single posting. Do not deduplicate by company/title alone. Canonicalize tracking parameters without losing identity-bearing parameters. Search the full known application history, not only the current page, and flag incomplete history.

## Which destinations change?

| Change | Destinations |
| --- | --- |
| Stage, priority, dates, next action, resume choice | Applications dashboard + Application Tracker |
| Career accomplishment or project update | Profile hub + Comprehensive Career Profile Doc |
| Reusable answer, letter or interview story | Relevant hub record + Career Writing Archive |
| Actual employer entry or attachment | Employer readback + application record + tracker summary |

Where a dashboard/hub is not configured, mark it pending; do not label two-destination sync complete. The document-only workflow is a usable reduced mode.

## Reliable write sequence

1. Read latest checkpoint, both destinations and relevant full sources; capture current revisions and user edits.
2. Reconcile one field-level change set. User decisions govern preferences; official posting sources govern posting facts; verified submission evidence governs Applied. Surface material conflicts without silently selecting one.
3. Record intended operation IDs. Apply targeted updates with revision checks where supported. If no conditional writes exist, re-read immediately before writing, use the smallest supported update and compare afterward. Never claim atomicity across systems.
4. Read back actual saved changed fields in each destination. An acknowledged write is not readback verification. Preserve a successful destination if the other fails.
5. Persist per-destination result and pending operations; on retry fresh-read and apply only unresolved changes. Prevent duplicate entries by stable identity and operation history.
6. Preserve history, human notes, document formatting/tabs/links and original found dates. Counts come from full current reads, not hardcoded totals.

Snapshots record the original read time, source and revision. Packet generation or changing a file timestamp cannot renew source freshness. Use an explicit freshness policy (24 hours is a reasonable application-packet default); revalidate fast-changing availability immediately before entry. Never invent verification receipts.

- **One destination failed:** preserve verified writes, fresh-read the failed destination and retry only its unresolved fields. Check for existing content to avoid duplicates.
- **Concurrent human edit:** compare before/current/proposed; retain human text and surface material conflict. Never force an old snapshot over a new revision.
- **Missing connection or sign-in:** record the exact user action; continue research/drafts. Never bypass policy or use extracted credentials.
- **Role no longer accessible:** mark blocked/unverified until evidence establishes closed; preserve history.
- **Changed resume/question:** invalidate affected review, retain prior artifacts, reverify the new version.
- **New chat/context loss:** read registry, current project instructions and latest checkpoint; fresh-read live records. Do not restart the interview or replay completed writes.
- **Missing dashboard capability:** keep a private document tracker working; record precisely which dashboard functions and data writes remain unavailable.

Always end a blocked run with current state, successful work, pending operations and an exact resume instruction. Never manufacture success receipts or mark partial setup complete.

# Internship Studio — runnable local dashboard

A working starter, not just a design brief. It runs locally with Python 3.9+ and its standard library (including SQLite). There are no package installs, API keys or paid services required for this local app.

From the repository root:

```sh
python3 dashboard/server.py
```

On Windows with the Python launcher:

```bat
py -3 dashboard/server.py
```

Open **http://127.0.0.1:8765**. Keep the terminal running; press Ctrl+C to stop. Use the printed `127.0.0.1` URL rather than `localhost`. If Python is missing, install a supported Python 3 version from [python.org](https://www.python.org/downloads/); your assistant can walk you through it. You can also use `Start Dashboard.command` on macOS or `Start Dashboard.bat` on Windows.

## Included

- Overview with priorities, counts and next actions.
- Applications with employer/requisition/official URL, term/location, stage versus availability, source and submission evidence, search/filter/sort, archive and next action.
- Application questions with prompts, drafts, grounding, conditions and review status.
- Career profile entries with personal contribution, maturity, sources and notes.
- Resume library with private PDF/source links, exact-version/hash metadata and review notes.
- Answer studio for reusable answers/stories and review.
- Manual sync checklist with separate records for each destination and evidence for readback.
- Workspace preferences and destination links.
- Persistent SQLite storage, revision conflict checks, retained history, Markdown export and JSON backup/restore.

Starts empty. The optional Overview demo button creates three explicitly fictional examples. It never discovers real roles or imports anyone's profile. Archive examples before real use, or try them with a separate data directory.

## Data stays outside the public checkout

The default data directory is `~/.internship-search-workspace`, containing `workspace.sqlite3`. This is local persistence, not browser localStorage. Closing the browser/server does not delete it. Files linked from resume records stay in their original private storage; this starter stores references, not PDF bytes.

For a separate test workspace or different port:

```sh
python3 dashboard/server.py --port 8766 --data-dir /absolute/path/to/private/test-workspace
```

Choose a private directory **outside** this public repository. Do not commit database files, backups, profiles or resumes. Exports contain private career information. JSON backup contains records plus history; restore only accepts an empty workspace and never overwrites existing records. Linked PDFs/source files need their own backups. Restore currently accepts backups up to 8 MB; for a larger workspace, preserve the database and plan a migration with your assistant.

## What still needs setup

This starter has **no Google Docs credentials, automatic sync, browser autofill, employer integration, PDF compiler, file upload storage, hosted account system or scheduler**. The sync checklist records actual work performed through the user's connected tools; it does not execute writes. Review/verification labels are user-entered assertions with evidence, not automated document inspection.

Use the onboarding pack to connect your own accounts. An assistant with authorized browser access can edit the local UI. It can also use the local API below from the same computer when authorized; it must read and reconcile current records and verify each cloud destination independently. A cloud-only ChatGPT session cannot automatically access this computer's loopback app.

## Local access boundary

The server binds only to `127.0.0.1`, validates Host/Origin, denies cross-site requests, requires a per-run token for data routes and serves only three allowlisted static files. Local session tokens are available to the browser on this computer; they are not an account/login system. Other processes or users with access to your OS account can access local data. Use an appropriately private device/account.

**Do not expose this server through a public tunnel, reverse proxy or network bind.** Python's [HTTP server documentation](https://docs.python.org/3/library/http.server.html) does not recommend it for production. For a private online dashboard, reuse these screens/data rules in an appropriate hosted backend with owner authentication and per-record/file authorization. Follow [the hosting handoff](../docs/10-dashboard-code.md) and test access before adding personal data. Do not host the static files alone and call it the complete app.

## Local API for authorized assistants

No CORS access is provided. Requests must target the exact printed Host. Do not place the session token in files, logs, source control or shared packets.

1. `GET /api/session` returns the per-run `token` in memory.
2. Include `X-Workspace-Token` in subsequent API requests. POST bodies use `Content-Type: application/json`.
3. `GET /api/state` returns all records: `{kind,id,revision,updated_at,data}`. Collections are `applications`, `profile`, `resumes`, `writing`, `sync`, `settings`.
4. `POST /api/save` accepts `{kind,id,expected_revision,data}`. Use a UUID for new IDs and revision `0`; existing records require the current revision. HTTP 409 means refresh/reconcile, not force overwrite. The server validates submission evidence, exact duplicate identities and review invalidation. Read `/api/state` back after saving.
5. `GET /api/history/{kind}/{id}` returns previous saved versions, newest first.
6. `GET /api/export` and `GET /api/export.md` export complete JSON history or readable current records.
7. `POST /api/restore` restores a dashboard JSON export only into an empty database. This is not a general template-import endpoint.

The blank templates elsewhere in this kit are conceptual records; the runnable UI's concrete fields are defined by `static/app.js` and validated by `server.py` (for example `company`/`url` rather than `employer`/`official_url`). Map fields explicitly and preserve unknown facts; do not post a template directly as a tested dashboard import.
